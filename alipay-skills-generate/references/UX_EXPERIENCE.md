# 通用体验契约

## §1 使用原则

生成 UI 前，先把 Gate A 的自然语言目标连接成总体用户动线，再确认每一步的结果、后续动作、参数来源、安全等级和承载方式。动作能否直接执行以 `SAFETY_POLICY.md` 为准。

执行时区分两类要求：

1. **硬边界**：平台能力、安全、参数来源和页面路径等必须遵守。
2. **体验决策**：动线、动作数量和承载方式由源码证据、用户目标、参数可靠性和业务风险决定。

生成体验时要保留判断理由。每个按钮、出口、半屏、原页面承接和不生成的动作，都应能说明证据、参数来源和取舍原因。

## §2 硬边界

1. 默认原子组件不得调用 `my.request`、`my.tradePay` 或 `my.getAuthCode`。声明 `scope.dynamic` 的动态组件可以按体验决策调用 `my.request`、`my.tradePay` 和定时器，包括在用户 tap 中直接执行读写请求；动态组件仍不得调用 `my.getAuthCode` 或其他未支持 API。`my.tradePay` 只用于用户明确点击付款 CTA 后进入平台支付确认。
2. Agent 入口与 UI 入口分别裁决。确定性点击需要原位请求，且请求实现及全部传递依赖均受组件支持时使用 `my.request`；否则操作意图和参数完整且目标 API 已注册时使用 `apiCall`，需要补参、语义理解或跨能力编排时使用 `followUpText`。`apiCall` 的参数必须来自接口结果、dataset、组件 data、`_meta`、页面 query 或用户已确认输入。
3. `relatedPage` 的 `query` 必传；`path` 如传入，必须来自源码中的 `navigateTo` / `redirectTo` / `switchTab` 等真实页面路径，不得编造。组件先调用 `setRelatedPage({ path?, query })` 配置目标，再在用户 tap handler 中调用 `openRelatedPage()` 打开。
4. `detailPage` 表示组件通过 `vctx.openDetailPage({ url })` 打开半屏承载页，路径必须来自源码真实页面或 `app.json` 注册页面。
5. 动作是否可直接执行按 `SAFETY_POLICY.md` 的 R0-R5 分级判定。R2 低风险可撤销写操作在参数可靠时可直接执行；R3 必须确认；R4 禁止 Agent 自动执行最终资金、身份或关键资料动作，只允许用户点击承接。
6. `structuredContent` 只承载业务语义字段，不写样式类名、布局状态或纯展示派生字段；展示派生逻辑放组件侧，内部链路信息放 `_meta`。
7. 参数来源不可靠、目标接口未注册、确认信息不完整或原流程依赖插件/复杂页面能力时，不生成直接操作，改用结果展示、半屏说明或 `relatedPage`。

## §3 源码事实输入

Gate D 从 `interface-spec.<scene>.md` 汇总以下源码事实。相同源界面的动作跨越多个分析场景时，按真实参数关系合并后再设计组件和接口。

| 线索 | 搜索对象 | 记录内容 |
|------|----------|----------|
| 用户目标 | 页面标题、tab、按钮文案、事件名、空态文案 | 用户想查询、筛选、选择、查看、确认、提交、跟踪、恢复 |
| 展示重点 | AXML 绑定字段、`setData`、列表渲染、详情页字段 | 影响用户判断的核心字段，不等于全量接口字段 |
| 操作证据 | `onTap` / `catchTap` / handler 名、按钮文案、表单提交 | 源码中真实存在的推进动作，以及点击后是立即执行还是进入确认/复杂流程 |
| 执行链 | handler、校验/确认、请求、`setData`、刷新、fail 分支 | 参数、成功后权威状态、连续点击顺序、失败回滚与防重复提交 |
| 参数来源 | dataset、页面 query、接口返回、storage、表单字段 | 能否可靠传给下一个 API、半屏或原页面 |
| 执行/承接事实 | 详情方法、业务接口、`navigateTo`、`switchTab`、query 参数 | 源码实际使用的请求、本地状态或页面承接链路，以及组件直接执行闭包证据 |
| 登录/授权 | 登录入口、授权方法、鉴权失败分支 | 登录是否为独立 API、卡片或页面；受保护业务请求如何校验已有 session；当前业务动作本身是否包含主动鉴权 |
| 安全等级/确认 | `showModal`、`confirm`、支付/退款/取消/删除/修改、购物车、下单等动作 | Gate C 标注的 safetyLevel、源码已有确认和动作后果 |
| 失败恢复 | fail 分支、错误文案、空态按钮、重试逻辑 | 失败后是重试、换条件、去登录、重新授权还是回原页面 |
| 过期条件 | 刷新、提交成功、状态变化、重新查询 | 旧卡片何时不应继续操作 |

Gate D 直接把这些事实写入现有 `design.md` 的总体用户动线、体验决策记录和源交互映射，不生成额外体验资产文件。

## §4 体验决策要点

Gate D 设计 schema、组件和出口前，逐项完成以下决策。

| 决策项 | 判断重点 |
|------|----------|
| 用户当前真正想完成什么？ | 用用户视角描述目标，不写技术实现 |
| 当前结果之后，用户自然会做什么？ | 区分主要下一动作和按需保留的次要动作，写明下一 Agent/UI 入口 |
| 当前结果是终态还是中间态？ | 中间态必须连接到下一步骤、页面承接或恢复出口，不能因 Agent 无权执行就提前终止 |
| 哪些动作有源码证据？ | 页面事件、接口、跳转、弹窗、错误处理、用户已确认需求 |
| 哪些动作只是推测？ | 没有证据或参数来源时，不直接生成交互 |
| 动作适合放在哪里？ | 卡片、半屏、原页面、上行消息、无 UI |
| 参数来源是否可靠？ | ID、状态、金额、地址、手机号等关键参数必须可追溯 |
| 动作是否改变业务状态？ | 按 SAFETY_POLICY 判定：R2 可直接执行并提供恢复出口，R3 需要确认，R4 只能用户点击承接 |
| Agent 和 UI 如何分别进入？ | `agentEntry` 负责承接自然语言意图，`uiEntry` 负责当前组件点击；两者分别裁决 |
| 失败、空态、过期或页面返回后怎么办？ | 重试、换条件、去登录、重新授权、调用明确的查询接口恢复或结束 |
| 未采用动作是否影响用户出口？ | 不生成不可控操作，同时保留合理承接路径 |

## §5 体验契约：总体用户动线与体验决策记录

Gate D 先在现有 `design.md` 中按代表性自然语言目标写出“用户说法 → 前置补参或上下文 → 所需业务结果或动作 → 主要下一动作 → 完成条件”的总体用户动线骨架，不预选 API 或 UI 入口。完成 D.2 接口设计和 D.4 入口裁决后，将骨架回填为以下最终顺序，再为每个有 UI 的组件产出 `体验决策记录`，不另建文件：

```text
用户说法 → 前置补参或上下文 → agentEntry → Result/组件 → 主要下一动作 → 下一 agentEntry/uiEntry → 完成条件
```

跨 Skill 时写明真实传递字段；使用 `detailPage` 或 `relatedPage` 时写明传入上下文、用户在页面完成的目标，以及返回对话后调用哪个查询接口恢复。Gate E 只能按总体动线和体验决策记录联合实现；若实现时发现不足，回到 Gate D 补决策，不得临时新增按钮、路径或接口调用。

- <组件名>

- <用户想完成的事情>

决策记录要求：

1. 以 Gate A 的自然语言目标、总体目标能力和 Gate C 的源可见动作为完整输入；先形成总体用户动线，再做逐组件记录。分析场景和 Skill 归属只组织实现，不缩减源交互范围。
2. 动作数量由用户目标、源码证据、参数可靠性、业务风险和卡片承载复杂度决定。
3. 卡片动作必须与当前用户目标相关；当动作较多、并列关系复杂、信息量过大或 safetyLevel 为 R3/R4 时，使用半屏、原页面或分步上行承接。
4. 保留动作和不生成动作都要有理由。没有证据、没有参数来源、风险不可控或原页面流程更完整，都是不生成的有效理由。
5. 展示字段服务于用户判断。卡片只保留决策所需字段；补充信息进入半屏或原页面。
6. 每个总体范围内的源可见动作必须写入源交互映射；整项点击、局部控件、父子事件、事件阻断、选中/禁用/售罄等状态按源码事实记录，不得只记录 handler 或接口名。
7. 允许差异只接受平台能力、安全边界、参数可靠性或卡片容量约束；Skill 划分、API 已存在、通用模板偏好或实现方便不能作为改变交互方式的理由。
8. 中间态结果必须把主要下一动作连接到明确的下一 `agentEntry`、`uiEntry`、完成条件或恢复入口。若 `userCanPerform=true` 且承接可靠，必须设置 `ctaRequired=true`，即使 `agentMayExecute=false`。
9. 只有 `userCanPerform=false` 或没有任何可靠执行/承接路径时才能省略 CTA；在 `executionFeasibility` 中写明依据。
10. 上游结果通过判别字段进入不同下游执行链时，逐个判别值复核 Agent 能力、参数传递和 UI 入口。用户已明确要求 Agent 完成的查询或详情能力，页面承接不能替代缺失的 Agent 调用链；缺少分支事实时回 Gate C 定向补齐。
11. 总体范围内用户可表达的动作必须有已注册的 `agentEntry`。最终动作需要用户手势或原页面完成时，复用能返回该动作摘要和 CTA 的查询、详情或 handoff API；只有 `userCanPerform=false` 或不存在可靠 Agent 承接路径时才使用 `none`。

### 5.1 Agent 入口、UI 入口与控件形态分离

`agentEntry` 表示 Agent 收到该自然语言意图后首先调用的已注册 API。它既可以直接执行动作，也可以查询最新状态并返回确认或页面承接 CTA；`agentMayExecute` 只表示 Agent 能否直接改变业务状态。最终动作必须由用户在页面完成时，优先复用能生成对应 CTA 的查询或详情 API；没有可复用入口且该动作属于总体范围时，设计原子 handoff API。不得仅因最终动作需要用户手势、半屏或原页面，就写成 `agentEntry=none`。纯展示状态的 UI 动作使用能提供相同信息的查询或详情 API 作为 Agent 入口，不为展开收起单独生成接口。

卡片上的用户操作另行裁决 `uiEntry`；是否存在 Agent API 不自动决定 UI 入口。确定性点击需要在当前卡片原位完成读写时，按 `JSAPI_BOUNDARY.md §3.2.1` 检查执行路径事实，再按 `JSAPI_BOUNDARY.md §3.4` 裁决入口。已有 session 执行路径的全部传递依赖均受组件支持，且业务 URL、method、header、后端参数映射和响应信封已收口到 `utils/` 业务函数时，必须使用动态组件 `uiEntry=my.request`；同一操作存在 Agent API 时必须复用该函数。两端可以分别保留对话参数编排和 UI 状态编排，组件不得 import 原子接口 handler。

`uiEntry` 只描述用户点击后如何执行，不决定控件形态。先根据源交互映射确定点击区域、控件形态、事件关系和状态反馈，再选择 `localState`、`my.request`、`tradePay`、`apiCall`、`detailPage`、`relatedPage`、`followUpText` 或 `none`；不得因存在 API 或出口就自动生成独立按钮、链接或其他可见入口。

`uiEntry=my.request` 表示动态组件在 tap handler 中直接或通过全部传递依赖均受组件支持的 `utils/` 业务函数调用平台请求，不发送上行消息。只有当前动作的已有 session 执行路径本身必然到达 `my.getAuthCode`、主动 token 换取或刷新、接口侧专属 JSAPI、接口私有状态或不可向组件暴露的凭证，或者直连会复制敏感请求逻辑时，才改用上行消息；项目或接口侧存在主动鉴权不是否决动态组件的证据。UI 意图和参数完整且目标 API 已注册时使用 `apiCall` 发送确定的 API 名和参数，Agent 不再做业务选择；任务仍需补参、语义理解或跨能力编排时使用 `followUpText`。不得把明确的加减、勾选、收藏或切换操作改写成待 Agent 重新理解的自然语言请求。

`uiEntry=tradePay` 表示动态组件在用户点击明确付款 CTA 后调用 `my.tradePay`。只在源码存在真实支付链、最新结果包含订单/商户/金额摘要与全部支付参数、平台仍提供最终支付确认时使用；调用前不得由 Agent 或组件代替用户确认，调用后必须区分成功、用户取消、明确失败和结果未知，并通过已注册查询 API 重查权威订单状态。条件不完整时改用 `detailPage` 或 `relatedPage`。

源页面使用整项点击、图标、步进器、Tab、筛选项、开关、选项或展开区时，在原子组件能力范围内沿用该交互载体。确需改变时，在允许差异中写明依据、影响和替代方式。

反向同样成立：没有注册 API 不等于没有用户出口。`ctaRequired=true` 时必须生成用户可感知的确认或 handoff 入口；`uiEntry=relatedPage` 时，可见入口的 tap handler 必须调用 `openRelatedPage()`，不能用单独的 `setRelatedPage` 或 `followUpText` 冒充页面承接。

## §6 出口选择规则

### 6.1 uiEntry 严格语义

| uiEntry | 严格含义 |
|----------|----------|
| `detailPage` | 通过 `vctx.openDetailPage({ url })` 打开半屏承载页；目标路径来自源码真实页面或 `app.json` 注册页面 |
| `relatedPage` | 先通过 `vctx.setRelatedPage({ path?, query })` 配置目标，`query` 必传、`path` 如传入则来自源码真实页面，再由用户点击调用 `vctx.openRelatedPage()` 打开 |
| `localState` | 只改变组件内展示状态，如展开收起、Tab、临时筛选和本地选中，不改变服务端状态 |
| `my.request` | 仅动态组件使用；在 tap handler 中直接或通过全部传递依赖均受组件支持的 `utils/` 业务函数执行有源码证据的读写请求，不发送上行消息，并以服务端状态校准组件 |
| `tradePay` | 仅动态组件使用；用户点击明确付款 CTA 后调用源码真实 `my.tradePay` 链路进入平台支付确认，完成后重查权威订单状态 |
| `apiCall(<apiName>)` | UI 已表达完整操作意图，发送精确 `api/call` 调用指定的已注册 API；不再让 Agent 选择接口、解释意图或重复确认 |
| `followUpText` | 只发送自然语言上行消息，将仍需补参、语义理解、确认意图或跨能力编排的任务返回 Agent 流程 |
| `none` | 终态展示，无可操作出口 |

### 6.2 选择提示


| 判断 | 倾向 |
|------|------|
| 只是展开、收起、Tab、临时筛选等本地状态 | 使用 `localState` |
| 确定性操作需要当前卡片原位更新，且已有 session 执行路径的全部传递依赖均受组件支持 | 必须使用 `my.request`；请求契约收口到 `utils/` 业务函数，同一操作存在 Agent API 时共同复用，写操作由用户 tap 触发并以服务端状态校准 |
| 操作意图和参数完整，但已有 session 执行路径到达组件侧不支持依赖 | 使用 `apiCall(<apiName>)` 上行调用已注册接口；点击后进入提交态并等待新 Result |
| 缺少必要参数，或需要语义理解、跨能力编排 | 使用 `followUpText` |
| 信息较多且已有页面可承载详情或确认 | 使用 `detailPage` |
| 购物结算、下单等已有真实小程序页面 | 半屏可行时优先 `detailPage`，用户在原页面完成；核心流程被拦截或缺上下文时降级为 `relatedPage` |
| 付款且源码存在真实 `my.tradePay` 链路、支付参数完整、平台保留最终确认 | 使用动态组件 `tradePay`；否则使用 `detailPage` 或 `relatedPage` |
| 涉及半屏不支持的插件、地图上下文或跨页路由 | 使用可靠 `relatedPage` |
| R3 不允许 Agent 自动执行但组件可完整确认和提交 | 展示具体确认信息后，由确认 tap 使用动态组件 `my.request`、`apiCall` 或可靠页面承接 |
| R4 不允许 Agent 执行但用户仍可继续 | 保留可见 CTA；支付满足 `tradePay` 契约时可由用户点击进入平台确认，其他场景优先验证 `detailPage`，不可行再使用 `relatedPage` |
| 需要用户补条件、确认意图或进行自然语言选择 | 使用 `followUpText` |
| 当前结果就是终点，或没有可靠下一步 | 使用 `none`，并说明原因 |

### 6.3 页面承接连续性

每个 `detailPage` 或 `relatedPage` 动作都必须在现有体验决策记录中闭合四件事：目标页面与真实 query、用户在页面完成的任务、打开前需要重查的状态、返回对话后用于恢复的已注册查询接口。平台不能自动感知页面完成结果时，业务 `SKILL.md` 明确引导用户返回后继续，并在继续执行状态变更、金额计算、结算或下单前重新查询；不得沿用承接前的旧卡状态。

## §7 组件实现要求

1. 按展示重点裁剪字段，长内容用半屏或 relatedPage 承接。
2. 动作组织服从总体用户动线、体验决策记录和源交互映射；突出当前目标的主要下一动作，次要动作按需收纳，模板阶段仅实现记录内动作及其约定的点击区域、控件形态和事件关系。
3. `apiCall` 的接口名和参数必须来自当前 Skill 的真实契约与数据源；组件不得复制业务 URL、鉴权或请求映射，也不得把确定性操作改写成待 Agent 理解的自然语言任务。
4. 使用 `uiEntry=my.request` 或 `uiEntry=tradePay` 的组件必须设置 `componentRuntime=dynamic`、声明 `scope.dynamic`。`my.request` 的复用依赖闭包必须符合组件运行时边界；请求可以读写，R2 由用户 tap 触发，R3 先展示具体确认信息再由确认 tap 触发，并具备提交态、防重复、服务端校准和失败恢复。R4 身份/关键资料动作不得由组件直接请求；付款仅在 `uiEntry=tradePay` 的严格契约下由用户点击进入平台确认。定时器不得发起写操作或支付。
5. `localState` 只用于无需网络的组件展示状态。需要业务请求的控件按原位交互需求、当前动作的可达依赖和意图完整度选择动态组件 `my.request`、`apiCall`、`followUpText` 或可靠页面承接，并实现对应的提交态、防重复触发、服务端校准、失败恢复和旧卡过期。
6. 登录/授权承接只能基于源码中确认的入口、接口或页面路径生成；源码使用独立登录能力时，受保护业务组件只显示鉴权失败状态，不复制登录流程。
7. 动作执行策略遵循 SAFETY_POLICY：R2 需要原位执行且已有 session 执行路径的全部传递依赖均受组件支持时，必须由动态组件调用 `my.request`；只能由接口侧安全执行时使用 `apiCall`。R3 展示具体确认信息后可由确认 tap 使用动态组件 `my.request`、`apiCall` 或页面承接执行；R4 只提供用户点击触发的平台支付或原页面承接入口，满足严格支付契约时平台入口可为动态组件 `tradePay`。
8. 空态、失败态、过期态必须有处理；不一定生成复杂 UI，但不能留下可误触的旧操作。
9. 如果组件无法可靠表达完整流程，保留关键摘要并提供合理承接，不强行复刻原页面。
10. `ctaRequired=true` 时必须实现清晰可见的继续操作出口；`relatedPage` CTA 必须在 tap handler 中调用 `openRelatedPage()`，不得用隐藏元数据、单独配置、`followUpText` 或拒绝文案代替。对应自然语言意图必须能通过 `agentEntry` 生成同一承接结果。
