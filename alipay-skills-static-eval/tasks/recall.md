# 召回与触发效果

评测 skill 能否在公域内被准确召回。关注 description 的意图表达是否清晰、SKILL.md 中的能力声明是否完整且不自相矛盾。

> 执行流程层面的前后矛盾由 `guidance` 任务负责，本任务只关注**能力边界**层面的矛盾。

## 评测方法

主 agent 已将 `name` 和 `description` 传给你。你只需读取 SKILL.md，然后检查以下问题：

### 1. 描述是否可匹配

`description` 是否足够具体，能让意图匹配系统将其关联到合理的用户 query？是否存在过于宽泛导致误召回的风险？

| ✅ 通过 | ❌ 不通过 |
|---|---|
| "帮助用户在鲜丰水果小程序中搜索水果、下单、管理订单和优惠券" | "帮助用户使用小程序"（无任何业务特征词） |
| "在星巴克小程序中点单、查看会员积分和优惠券" | "提供便捷的服务体验"（太空泛，什么 skill 都能套） |

### 2. 能力声明是否存在

SKILL.md 中是否有明确的能力列表或功能描述段落？

| ✅ 通过 | ❌ 不通过 |
|---|---|
| SKILL.md 中有「## 能力」章节，列出搜索商品、加入购物车、提交订单、查看订单状态等 | SKILL.md 只有一段欢迎语，没有列出任何具体功能 |
| SKILL.md 用自然语言描述了「本技能可以帮助用户完成以下操作：…」 | name 和 description 有值，但 SKILL.md 内容为空或仅有一行占位文字 |

### 3. 支持范围与限制范围是否完整、无矛盾

- SKILL.md 中是否**同时**出现了「能做」和「不能做」的表述？
- 交叉比对支持声明和限制声明，是否存在逻辑冲突？

| ✅ 通过 | ❌ 不通过 |
|---|---|
| 「支持充值全流程，不支持非大陆手机号」— 同时声明了能做和不能做，且无矛盾 | 全文只有「支持/可以/能」，没有任何「不支持/仅支持/不能/禁止」— 边界缺失 |
| 「支持搜索水果、支持下单，不支持跨城市配送」— 无矛盾 | 「支持修改订单」但另一处写「不支持修改已支付订单」且未区分状态 — 逻辑冲突 |
| 「支持查询订单，不支持取消订单」— 边界清晰 | 「支持所有支付方式」但后文写「仅支持余额宝支付」— 自相矛盾 |

### 4. 对话式交互能力是否覆盖

小程序 AI 场景下，用户倾向于用自然语言完成全流程。检查 SKILL.md 是否声明了对以下交互模式的支持（适用时）：

- **承接模糊意图**：用户表达非结构化需求（如「想喝点清爽的」「最近有什么推荐」）时，是否有由 AI 理解并推荐的路径，而非要求用户给出精确关键词。
- **自然语言修改**：用户能否在对话中直接修改规格、时间、地点等枚举值或明确实体的字段，而非跳出对话重新走流程。
- **历史与资产可查可操作**：高频场景下「再来一次上次的」「用积分兑换优惠券」这类基于历史数据/个人资产的指令，是否有对应路径。
- **服务进程动态更新**：涉及订单/服务状态的场景，是否说明随状态推进动态更新，而非静态展示后不再变化。

> 这四点是**对话式交互的设计期望**，不是每个 skill 都必须全具备。判定时结合 skill 的业务场景：与上述模式强相关的（如点单、预订、查询类）缺失才记问题；纯工具型 skill（如单一查询）按需豁免。

| ✅ 通过 | ❌ 不通过 |
|---|---|
| 点单 skill 声明了「模糊推荐 → 确认 → 下单」「可对话改杯型/糖度」「可『再来一杯上次的』」 | 点单 skill 只支持精确关键词搜索下单，对「推荐」「改杯型」「再来一杯」全无路径 |
| 涉及订单状态的 skill 说明卡片随状态推进更新 | 下单后卡片静态展示，用户无法感知支付/出餐等状态变化 |

> 能力**未声明**不等于运行时缺失 — 可能由 tool 返回或组件逻辑兜底。仅当 skill 业务场景明显需要、却完全无路径时标记为**潜在缺陷**，建议动态评测验证。

## 输出

只报告发现的问题，通过项不列。每个问题附带一条改进建议。

```
## [skill 名称] — 召回与触发

### 问题
- [缺陷/潜在缺陷] [问题简述]
  - 位置：[SKILL.md 段落或行号，或 description 字段]
  - 原文：[相关引用]
  - 影响：[对召回或触发的影响]
  - 建议：[针对该问题的改进方向]
```

如果未发现任何问题，报告一句话：「未发现召回与触发相关问题。」
