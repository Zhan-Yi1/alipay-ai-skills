# 指引与示例质量

评测 SKILL.md 中的 SOP/指引是否能让 agent 准确执行，以及和 mcp.json 的声明是否一致。

**重要前提**：mcp.json 定义了 tool 的名称和 input schema，但**看不到运行时的返回内容**。因此无法判断 tool 的返回 message 是否会补足 SKILL.md 的缺失。对于 SKILL.md 中看似不足、但运行时可能被 tool 返回兜底的场景，标记为「潜在缺陷」并建议开发者通过动态评测验证。

## 输入

- skill 的 `SKILL.md`
- skill 的 `mcp.json`

## 评测项

### 1. 步骤是否可执行

每个步骤是否给出了足够的信息让 agent 行动，还是含糊的概括。

| ✅ 通过 | ❌ 缺陷 |
|---|---|
| 「调用 `queryOrder` 查询订单状态，若 status=paid 则调用 `sendNotification`」— 明确了工具名和判断条件 | 「处理订单」— 只写了步骤名称，没说调哪个工具、怎么判断 |
| 「读取用户输入中的手机号，校验是否为 11 位数字」— 明确了输入来源和校验规则 | 「获取必要信息」— 没说从哪获取、获取什么 |

> 若步骤中有工具调用但未写明后续判断逻辑（如「调用 createOrder」后没写成功/失败分别怎么做），标记为**潜在缺陷** — 运行时 tool 返回可能兜底，静态无法确定。

### 2. 参数提取指引

当 tool 的入参不是直接来自用户输入、而是来自上游 tool 的返回值或需要推导计算时，SKILL.md 是否明确了提取或计算方式。

| ✅ 通过 | ❌ 缺陷 |
|---|---|
| 「从 `createOrder` 的返回中取 `data.orderId`，作为 `queryOrder` 的入参」— 明确了来源和字段路径 | 「调用 `queryOrder` 查询订单」— 没写 orderId 从哪来 |
| 「用户说'上次的订单'时，先调 `queryRecentOrders` 取最近一条的 id」— 明确了模糊输入如何解析 | 上一个 tool 返回 `{ list: [{ id, name }] }`，下一步需要 `shopId`，但没写要从 list[0] 还是用户选择中提取 |
| 「用户说'大杯'→ 传 `size: 2`；'中杯'→ `size: 1`」— 明确了自然语言到枚举值的映射 | 参数是枚举但只写「传入杯型」，没写「大杯/中杯/小杯」分别对应什么值 |

> 能比对上一步返回字段和下一步入参字段名一致的（如返回 `orderId` 且下一步入参也叫 `orderId`），不算缺陷 — agent 通常能自动推断。

### 3. 拒绝规则与话术

根据 skill 的能力范围判断。scope 简单、边界自明的 skill 不需要显式拒绝规则。scope 较宽、存在似是而非的越界场景时才需要。

| ✅ 通过 | ❌ 缺陷 |
|---|---|
| 「用户要求外送 → 告知'目前仅支持到店自提'」— 有触发条件 + 具体话术 | scope 较宽（涉及订单、支付、配送等多类操作），但完全没有任何拒绝/不支持/超出范围的描述 |
| scope 很小（如只做「查询天气」），边界自明，无拒绝规则也合理 | scope 宽且只写了拒绝条件但无回应用户的话术 |

> 有拒绝条件但无话术的，标记为**潜在缺陷** — tool 的失败返回 message 可能就是话术，静态看不到。

### 4. 决策分支是否封闭

每个分支条件是否都有明确的出口，不存在「if 失败 → 后面什么都没写」的悬空分支。

| ✅ 通过 | ❌ 缺陷 |
|---|---|
| 「若 success=false → 返回错误信息给用户」— 两个分支都有处理 | 「若失败 →」后面什么都不写 |
| 「若 total>0 → 进入步骤 2；否则 → 告知用户无结果」— 正反都封闭 | 只写了正常路径，异常路径全部缺失 |

> 正常路径完整但某些异常分支未展开的，标记为**潜在缺陷** — tool 的错误返回可能自动处理。

### 5. 工具声明一致性

SKILL.md 中引用的工具是否在 mcp.json 中都有声明，且名称和参数名一致。

- **工具名称**：SKILL.md 提到的工具名在 mcp.json 中是否存在；mcp.json 中声明的工具是否在 SKILL.md 中被引用
- **参数名称**：如果 SKILL.md 中明确写了传给某个 tool 的参数名（如「传入 `orderId`」），检查 mcp.json 对应 tool 的 `inputSchema` 中是否存在同名参数。参数名不一致会导致 agent 调用失败

以下情况视为缺陷：

- SKILL.md 提到了某个工具名但 mcp.json 中没有
- mcp.json 中有工具声明但 SKILL.md 从未提及（多余声明，可能是废弃工具）
- SKILL.md 写的参数名与 mcp.json inputSchema 中的参数名不一致（如 SKILL.md 写 `orderId`，schema 中是 `order_id`）

### 6. 接口 description 写法

检查 `mcp.json` 中各 tool 的 `description` 是否便于模型准确选接口。

- **首句声明业务对象，而非入参**：首句先点明「这是什么」，再描述按哪些维度检索。首句强调入参、或业务对象语义过宽（如「商品」覆盖多个类目），模型容易误命中。
- **不写内部实现细节**：实现细节对模型选接口无帮助，挤占「使用边界」信息。
- **职责单一、描述不重叠**：接口之间避免包含关系，描述面向模型而非用户，措辞简洁。
- **接口名语义化**：推荐「动词+名词」小驼峰（如 `searchDrinks` 优于 `search`）。

| ✅ 通过 | ❌ 缺陷 |
|---|---|
| 「搜索饮品。按关键词、温度、杯型检索…」— 首句点明业务对象 | 「按关键词、温度、杯型搜索商品列表」— 首句强调入参，且「商品」语义过宽 |
| 描述只写功能、调用时机、不适用场景 | 描述里写满了「先查库存再校验权限再…」的实现流程 |

> 接口名是否「语义化」是建议而非硬约束，命名过泛（如 `search`、`handle`、`process`）时标记为**潜在缺陷**，不强制改名。

### 7. 字段 description 写法

检查 `mcp.json` 各 tool `inputSchema` 中字段的 `description` 是否能指导模型正确填参。

**普通字段**：举例时给**多个不同样本**（避免被当默认值），并配明确的**缺省处理**。单一举例容易被模型当「标准答案」照搬。

**ID 类字段**：业务 ID 容易被按格式凑出，需在 `description` 中**显式声明取值来源接口**，并禁止从用户自然语言推断或使用示例值。

| ✅ 通过 | ❌ 缺陷 |
|---|---|
| `"keyword": "饮品关键词，例如『拿铁』『美式』『奶茶』。用户未说出具体饮品时不要填本字段，应改走推荐接口"` — 多样本 + 缺省处理 | `"keyword": "饮品关键词，如『拿铁』"` — 单例易被当默认值，且无缺省处理 |
| `"drinkId": "取自 searchDrinks 返回的 drinkId 原值，不要从自然语言推断"` — 声明来源 | `"drinkId": "饮品 ID"` — 未声明来源，模型可能从「那个拿铁」凑值 |

> 字段 `description` 缺失或仅写类型（如 `"string"`）时，标记为**潜在缺陷** — 字段级约束是模型填参的核心位置，缺失会显著降低准确率，但运行时可能被 SKILL.md 长文兜底，建议动态评测验证。

### 8. 信息源错位

检查内容是否写在了错误的信息源位置，导致模型在关键决策点读不到。

- **接口本身的功能**应写在 `mcp.json` 的 `description`，**不应**写到 `SKILL.md`。`SKILL.md` 中的接口清单只写「前置条件 + 上下游关系」。把接口功能写到 SKILL.md 会导致长文膨胀、与 `mcp.json` 易不一致。
- **跨多接口的业务规则**应写在 `SKILL.md`，**不应**写到单个接口的 `description`。写在单接口 description 里，只有调用该接口时才生效，其他接口决策时模型读不到。

| ✅ 通过 | ❌ 缺陷 |
|---|---|
| SKILL.md 接口清单只写「调用前需先登录」「依赖 searchDrinks 返回的 drinkId」 | SKILL.md 把某接口的功能、入参维度完整复述了一遍（与 mcp.json description 重复） |
| 跨接口的「下单后必须等支付完成才能查询」写在 SKILL.md | 跨接口的支付串行约束写在 `createOrder` 的 description 里 — 查询接口决策时读不到 |

> 此项需结合 mcp.json 与 SKILL.md 交叉阅读判断。仅当能明确判断「内容写错位置」时才记缺陷；模棱两可的标记为**潜在缺陷**。

### 9. 参数取值边界

检查 `mcp.json` 各 tool 的 `inputSchema`，对**用户可控**的参数是否给出了确定性的取值边界。

**判定主轴**：先判断该参数是否存在合理的**静态上限**。

- **有静态上限** → 必须加边界。典型：自由文本（长度上限）、金额（范围）、时间范围等。要求 `minimum`/`maximum`/`minLength`/`maxLength` 或等价的业务范围约束。有上限却没加 → 缺陷。
- **无静态上限**（无法提前预知合理值）→ 不强求。典型：分页、批量。其边界应由后端硬限制或分批逻辑兜底，在 schema 里拍一个数字反而会误伤正常请求或形同虚设。
- **固定枚举** → 枚举本身即边界，豁免。
- **纯派生** → 只读查询中完全由上下文或前置工具返回派生的内部参数，豁免。

| ✅ 通过 | ❌ 缺陷 |
|---|---|
| `amount` 有 `minimum: 0.01`、`maximum: 50000`（有静态上限，已加） | `amount` 是数字但无任何上下限（有静态上限却没加） |
| `phone` 有 `minLength: 11`、`maxLength: 11`（有静态上限，已加） | `remark` 自由文本无 `maxLength`，可被灌入超长内容（有静态上限却没加） |
| `pageSize` 无 `maximum`（无静态上限，不强求） | `size` 是固定枚举 `[1, 2, 3]` — 枚举豁免 |

> **判定理由**：模型不能靠世界知识可靠拦截用户的恶意或越界请求，必须依靠 schema 里确定性的工程约束来拦。把越界拦截寄托在模型「应该知道」上不可接受。

### 10. 空白状态可完成性

skill 是否强依赖登录、订单、购物车、门店、商品、历史上下文等状态？若是，检查是否覆盖了从空白状态进入的路径。

- 强状态依赖，但 SKILL.md **完全没有**未登录、空结果、默认推荐、补充信息或失败退出处理 → **潜在缺陷**
- 已有部分处理，但首次使用、无历史、无缓存等路径不完整 → **潜在缺陷**

| ✅ 通过 | ❌ 潜在缺陷 |
|---|---|
| 未登录时引导登录；购物车空时提示去选商品；无订单时给默认推荐 | 强依赖登录态，但未登录场景完全没写 |
| 历史为空时走「无历史」分支给新用户引导 | 只写了有历史/有数据的正常路径 |

> 标记为**潜在缺陷**：开发者可以在 **tool 的返回结果里**写引导话术（如未登录时返回「请引导登录」、空结果时返回「建议推荐商品」），这类兜底静态看不到。SKILL.md 未写不等于运行时缺失，建议通过动态评测验证。不强依赖状态的 skill（如纯查询天气）此项可跳过。

### 11. 禁止编造结果约束

SKILL.md 是否声明了：工具无返回、查询失败或证据不足时，agent 必须如实告知用户，不得伪造业务结果。

| ✅ 通过 | ❌ 潜在缺陷 |
|---|---|
| 「查询失败或无结果时，告知用户当前无法查询，不要编造订单信息」 | 全文未提及失败/无返回场景下如何回应用户 |

> 标记为**潜在缺陷**：开发者可以在 **tool 的返回结果里**写指导模型的话术（如「查询失败，请告知用户不要编造」），这类约束静态看不到。SKILL.md 未写不等于运行时缺失，建议通过动态评测验证 tool 返回是否已兜底。

### 12. 示例覆盖

是否提供了 agent 可参照的端到端执行示例。示例是给 agent 看的文档内容，不能靠运行时补足。

| ✅ 通过 | ❌ 缺陷 |
|---|---|
| 「用户输入：帮我充 100 元话费 → 校验号码 → 调用 createOrder → 调用 tradePay → 返回支付结果」— 从输入到输出的完整链路 | 只有零散的工具调用片段，无完整流程 |
| 同时给出了正常路径和至少一个异常路径示例（如充值失败、号码无效） | 只给了正常路径，异常情况完全没有示例 |

## 输出

只报告发现的问题，通过项不列。严重程度分两档：

- **缺陷**：SKILL.md 明确不足，无法靠运行时兜底。建议直接修改 SKILL.md。
- **潜在缺陷**：SKILL.md 看似不足但运行时 tool 返回可能兜底。建议开发者通过动态评测验证。

```
## [skill 名称] — 指引与示例质量

### 问题
- [缺陷/潜在缺陷] [问题简述]
  - 位置：[SKILL.md 或 mcp.json 中的段落/行号]
  - 原文：[相关引用]
  - 影响：[对 agent 执行的影响]
  - 建议：[改进方向；潜在缺陷应建议通过动态评测验证]
```

如果未发现任何问题，报告一句话：「未发现指引与示例相关问题。」
