# 安全性与用户体验

检查 skill 是否存在敏感信息泄漏风险，以及异常路径下用户是否会陷入不可预期的状态。

**不是 linter，不要机械匹配模式。** 阅读代码和配置，理解实际语义，基于上下文做判断。

## 输入

- skill 目录下的所有 JS/TS 文件
- skill 的 `mcp.json`
- skill 的 `SKILL.md`

## 评测项

### 1. Tool 返回可能含敏感信息

Tool 的返回结果会进入 agent 的上下文，agent 可能在后续对话中无意识泄漏。检查 `mcp.json`：

- tool 名称是否暗示返回凭据类数据（如 `getToken`、`getCredentials`、`fetchApiKey`、`getSecret`）
- tool 的 `description` 是否提及返回 token、key、secret、签名等敏感信息

如果 tool 确实返回凭据，这本身就是风险 — agent 拿到 token 后可能在 prompt injection 等场景下被诱导吐出。

**修复建议**：当原子组件需要原子接口返回的敏感数据时，把敏感数据放在接口返回的 `_meta: {}` 字段里。`_meta` 不会进入模型对话上下文，但组件能取到，从而避免敏感信息泄漏进 agent 上下文。

### 2. Tool 入参暴露敏感字段

检查 `mcp.json` 中各 tool 的 `inputSchema`：

- 参数名是否包含 `apiKey`、`secret`、`token`、`password`、`accessKey` 等
- 这意味着开发者让 agent 处理明文密钥，密钥会进入 agent 上下文

### 3. 异常路径是否完整

阅读每个关键操作（网络请求、工具调用、数据处理）的执行流程，回答：

- 如果这里失败了，接下来会发生什么？
- 用户会看到或被告知什么？
- agent 是否有足够信息决定下一步？

关注的是**流程是否完整**，不是某个特定语法是否存在。

### 4. 取消和中断

如果 skill 涉及多步操作（例如先下单、再支付、再查询结果），思考：

- 用户在步骤之间取消，状态是否会残留？
- 超时场景下是否有清理逻辑？

> 静态分析难以完整验证运行时行为，除非有明确的流程缺口，否则标记为潜在缺陷并建议动态评测。

### 5. SKILL.md 中的安全约束

SKILL.md 是否对不可逆操作（支付、退款、删除等）要求 agent 向用户二次确认。

## 输出

```
## [skill 名称] — 安全性与用户体验

### 问题
- [缺陷/潜在缺陷] [问题简述]
  - 位置：[文件:行号 或 mcp.json 中的 tool 名]
  - 原文：[相关代码/配置片段]
  - 分析：[为什么这构成风险，基于什么上下文]
  - 建议：[改进方向；潜在缺陷建议动态评测验证]
```

无问题则一句话：「未发现安全性与用户体验相关问题。」
